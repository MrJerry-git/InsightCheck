# InsightCheck 2.0 多系统体检平台：设计、分工与验收

日期：2026-09-20。状态：待实施的团队任务书，不是已发布软件版本。

本文件替代 TEAM_TASKS_V1.md、TEAM_TASKS_V1_COMPLETE.md 的当前分工，并优先于 IMPLEMENTATION_DESIGN.md、ROADMAP.md 中冲突的阶段安排。旧文件保留为历史记录。本次发布的是设计与任务，不表示 2.0 功能已经完成。

## 一、目标与完成的含义

按用户最新决定，不再以单一疾病作为全平台开发前提。建设覆盖常见基础体检类别的可扩展平台：账户、档案、资料导入校对、多系统历史与异常汇总、规则推荐、三档预算方案、审核、报告、问答和管理运行全部真实可用。只把确实需要病例数据才能完成的训练、校准和效果验证独立出来。

2.0 的完整性分两张清单验收：

1. **产品与规则流程**：本轮必须全部实现，不允许以空页面、假 API、硬编码成功或演示专用流程交付。
2. **数据依赖能力**：逐任务记录未接入/已接入/待评估，包括疾病模型、学习排序、微调和临床效果。未接入模型不阻断有依据的规则推荐，但不产生虚构疾病概率，不称“全部疾病预测已实现”。

“全覆盖”指已登记的体检类别和指标能够被录入、导入、查询、比较和纳入统一流程，不等于基础体检能查出所有疾病，也不承诺穷尽所有疾病名称。疾病目录按体检发现关联扩展；每个映射记录出处与版本。异常指标、可能关联的健康问题、确诊疾病和未来风险分别存储与呈现。

原始 CT/MRI 图像的自动检出、分割和诊断不作为本轮报告处理功能；保存附件与解析影像报告必须实现。无自有训练数据不是推迟 OCR、问答、规则引擎或文件导入的理由，可复用现成组件/模型。

## 二、覆盖清单与统一信息结构

首批目录以下表作为工程类别覆盖清单，不是推荐每个人做全部项目的套餐，也不是已经完成医学审定的项目表。实际条目、单位、参考区间及依据由任务产出登记；不同机构套餐通过版本化配置表达。

| 类别 | 需要支持的信息形态 |
| --- | --- |
| 基础信息与问卷 | 身高、体重、血压等测量，既往史、用药、家族史、生活方式与症状描述 |
| 一般体格及专科检查 | 内外科、眼耳鼻喉、口腔及适用的专科检查文字结论 |
| 血常规 | 数值、单位、参考区间及报告异常标记 |
| 尿液与粪便检查 | 数值、定性结果、镜检和报告描述 |
| 肝肾功能及生化 | 多指标、不同单位、方法和标本信息 |
| 糖代谢、血脂及其他代谢项目 | 数值、检测条件、历史变化 |
| 心电图及功能检查 | 文字结论、附件及可用结构化测量 |
| 超声和放射影像报告 | 部位、报告所见/结论、可追踪病灶及原文位置 |
| 按机构套餐启用的扩展项目 | 甲状腺、感染筛查、肿瘤标志物等作为可配置项目，不默认要求人人检查 |

不强制所有项目套用数值折线图：数值显示趋势，定性结果显示状态时间线，文字结论保留对照，病灶单独关联。未知指标保留原始内容并进入待映射队列，不丢弃、不自动解释。

统一字典至少包含：项目/指标稳定编码、名称和别名、类别/系统、值类型、原始与标准单位、参考区间来源及适用条件、可追踪属性、来源和版本。检查项目与疾病采用多对多关联，关联不代表确诊。既往诊断记录必须携带来源。

| 编号 | 必做任务 | 验收要点 |

| H04 | PDF/图片 OCR 与结构抽取 | 接入实际可运行组件；公布支持版式，用自制报告验证页码/原文定位与校对结果 |
| H05 | 跨系统趋势及异常整理 | 参考区间有来源及适用条件，无法比较时说明；不编造通用阈值和未来数据 |
| H06 | 多部位影像报告及病灶匹配服务 | 支持报告字段与人工修订回算；不将不同部位强行关联，不声称原始 CT 诊断 |
| H07 | 规则内容、候选生成与确定性排序服务 | 规则有依据/版本/适用条件；跨系统去重、理由、缺失信息提示；不等同 DeepFM 已接入 |
| H08 | 结构化解释与真实语言模型问答 | 使用当前记录、方案与可追溯依据；引用不存在时不编造；保护计算结果不被重写 |
| H09 | 模型任务注册与可替换适配器 | 分别定义疾病目标、人群、输入、时间窗、输出、来源、版本和缺失状态；保留 LightGBM/DeepFM 接入路径 |
| H10 | 可复用模型/组件清单与实际接入 | OCR/抽取/问答优先；检查权重、许可、预处理、资源与运行证据，不为等风险模型拖延其余功能 |
| H11 | 九华数据接入准备 | 字段映射模板、质量摘要、匿名标识及数据导出契约；标签和随访是否存在标为待核验 |
| H12 | 自制样例、内容覆盖清单与服务联调 | 各类别至少有可运行样例；数值/定性/文字/病灶及失败情形均有测试，协助 T04/T05/T10 接通 |

参考资料是规则与字典的依据，不是用于训练的病例数据。本轮应完成来源核验及可审阅的规则集，不要求现在咨询专家；未经审核的规则状态保留，不能宣称医学审核通过。没有足够依据的条目保留资料展示与待复核，不强行给出推荐结论。

规则推荐必须在没有疾病模型时独立产生可解释候选与方案，因此不属于可整体留空的数据依赖部分。现成语言模型需要凭据/算力时尽早提出；只有接口和模板回退不算真实模型问答完成。外部调用用合成资料联调，密钥不进入 Git 或前端。

## 八、接口交接与实施顺序

M0：王天一汇总 V2_API_CONTRACT.md（实施交付物，当前尚未生成），包含 endpoint、方法、请求/响应、权限、错误、版本和样例；王宏锦负责解析/分析服务契约及目录初稿；陈子正对齐全部页面。三人使用同一稳定编码，不各造字段。

最低资源集合：账户/会话、档案、检查记录、导入任务与校对、目录映射、分析运行、能力任务注册、三档方案及修订/审核、价格/规则管理、报告、问答。可复用旧 endpoint，但必须明确实际路径并保持旧方案可读。

M1：账户—档案—多类型导入—校对入库—历史查询。C01—C05、T01—T03/T08、H01—H05 优先，尽早合并真实链路。

M2：跨系统分析—规则候选—预算三档—修改审核—快照。C06—C09、T04—T07、H06—H07/H09 联合完成。风险未接入时仍能走通规则方案。

M3：报告—问答—管理—启动部署—备份恢复。完成其余任务，接入可用 OCR/语言模型，清除开发假接口。

M4：共同执行下述验收，逐项记录结果和证据。所有 PR 标任务编号、可运行路径、依赖和剩余项；小批提交，不堆到最后一次集成。不能以“接口已交付”为理由拒绝修复联调问题。

### 按任务建分支、按功能提交 PR

1. 每项新任务从最新 origin/main 建立短期分支，名称描述功能：feat/ 用于新功能，fix/ 用于修复，docs/ 用于文档。负责人记录在任务书与 PR 中，不以人名或整个阶段划分分支；表中名称只是示例，不要求一次创建全部分支。
2. 一个分支对应一项或一组紧密相关、可独立验收的改动。PR 尚未合并时，只向该分支提交与该任务相关的修改；另一项独立工作另建分支，不能混入在审 PR。
3. 三人的代码所有权不变。前后端通过契约协作；需要后端先完成的任务在 PR 写明依赖，依赖未就绪可开 Draft PR，但假接口不算联合验收通过。默认各分支均从 main 开始，不私自基于别人的未合并分支叠加任务。
4. PR 描述列明负责人、C/T/H 任务编号、具体结果、接口依赖、验证步骤和未完成项。优先小批合并，不积累为整个阶段的大 PR；张家睿审查后合并。自己的 PR 不能自我 Approve；管理员例外仅在完成实际审核后明确使用，不代替审核。
5. 开始任务前获取最新主分支；开发期间涉及共享接口或准备合并时同步 main，处理冲突后重新验证受影响流程。共享分支不强制推送、不通过整文件覆盖解决冲突。默认使用 Create a merge commit 保留提交与 PR 合并记录。
6. PR 确认合并、且分支没有合并后新增提交或其他依赖后，删除对应远程和本地任务分支。下一项工作从最新 main 重新开始，不复用已结束分支。
7. 现有 dev-czz/dev-wty/dev-whj/dev-jerry 及其他历史分支不批量删除。由负责人逐一核对未合并提交、打开的 PR 和本地未提交工作；有工作先保留或迁移并验证，无剩余工作再清理。迁移同一任务时避免新旧 PR 同时等待合并。

具体命令及收尾步骤见 [Git 协作与环境重建](CONTRIBUTING.md)。本节替代旧任务书中的个人长期分支及整阶段分支建议。
